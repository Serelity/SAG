# 04 - 排障记录

本文记录搭建 RAGFlow 过程中的问题、根因和处理方式。

## 1. Docker Desktop WSL Integration 挂载异常

### 现象

在 `RAGFlow-Ubuntu` 内检查 Docker Desktop WSL 集成文件时：

```bash
ls /mnt/wsl/docker-desktop/docker-desktop-user-distro-proxy
```

报错：

```text
No such file or directory
```

并且：

```bash
/mnt/wsl/docker-desktop/docker-desktop-user-distro
```

一开始是 0 字节空文件。

### 根因判断

Docker Desktop 与 WSL 的生命周期状态异常，导致 Docker 的用户发行版集成文件没有正确挂载。

### 处理方式

执行完整冷重启，使 Docker Desktop 和 WSL 重新建立集成状态。

### 验证结果

后续检查：

```bash
stat /mnt/wsl/docker-desktop/docker-desktop-user-distro
findmnt -T /mnt/wsl/docker-desktop/docker-desktop-user-distro
```

确认文件变为真实挂载，大小约 20MB，权限为 `0755`。

## 2. Windows 本机 MySQL 占用 3306

### 现象

PowerShell 检查监听端口：

```powershell
Get-NetTCPConnection -State Listen -ErrorAction SilentlyContinue |
  Where-Object LocalPort -In $ports |
  Select-Object LocalAddress,LocalPort,OwningProcess
```

发现 `3306` 被 `mysqld.exe` 占用。

服务名：

```text
MySQL80
```

### 处理方式

不停止 Windows 本机 MySQL。修改 RAGFlow Docker 部署副本中的 `.env`：

```text
MYSQL_PORT=3306
EXPOSE_MYSQL_PORT=13306
```

### 结论

- 容器内部 MySQL 仍然监听 `3306`。
- Windows 宿主机访问 RAGFlow MySQL 时使用 `13306`。

## 3. Docker Hub 拉取 MySQL 镜像 EOF

### 现象

执行 `docker compose pull` 时：

```text
failed to resolve reference "docker.io/library/mysql:8.0.40"
Head "https://registry-1.docker.io/v2/library/mysql/manifests/8.0.40": EOF
```

### 根因判断

网络或 Docker Hub 请求临时失败。

### 处理方式

先单独拉取：

```powershell
docker pull mysql:8.0.40
```

成功后重新执行：

```powershell
wsl -d RAGFlow-Ubuntu -- bash -lc "cd ~/deploy/ragflow-v0.26.4 && docker compose -f docker-compose.yml pull"
```

### 结论

单独拉取成功后，Compose 全量拉取成功。

## 4. ragflow-cpu 反复重启

### 现象

日志出现：

```text
tools/scripts/run_migrations.sh: No such file or directory
```

容器 `RestartCount` 持续增加。

### 根因判断

官方 Compose 中存在本地文件挂载：

```yaml
- ./entrypoint.sh:/ragflow/entrypoint.sh
```

该挂载会覆盖镜像内置入口脚本。本地 `entrypoint.sh` 依赖：

```text
tools/scripts/run_migrations.sh
```

但当前镜像 `infiniflow/ragflow:v0.26.4` 内没有这个脚本，因此启动失败。

### 处理方式

只修改 WSL 部署副本：

```text
~/deploy/ragflow-v0.26.4/docker-compose.yml
```

注释掉两处挂载：

```yaml
# - ./entrypoint.sh:/ragflow/entrypoint.sh
```

然后重建 `ragflow-cpu`：

```powershell
wsl -d RAGFlow-Ubuntu -- bash -lc "cd ~/deploy/ragflow-v0.26.4 && docker compose -f docker-compose.yml up -d --force-recreate --no-deps ragflow-cpu"
```

### 验证结果

```text
RestartCount=0
Status=running
```

日志出现：

```text
RAGFlow server is ready
RAGFlow admin is ready
RAGFlow ingestion is ready
```

## 5. SubAPI 模型配置失败

### 现象

RAGFlow 前端报：

```text
Your API key is invalid.
No valid response received
```

后端日志出现：

```text
Model "gpt" is not supported by any configured account in this group
```

### 根因判断

- `gpt` 不是可用模型名。
- SubAPI 给出的截图示例是 Codex CLI 的 `Responses API` 配置。
- RAGFlow 当前 OpenAI-Compatible 代码路径使用的是 `chat.completions.create` 和 `embeddings.create`。

### 当前结论

如果 SubAPI 没有明确提供：

```text
/v1/chat/completions
/v1/embeddings
```

则不能直接作为当前 RAGFlow 的完整模型供应商。

## 7. 10 万行 TSV Demo 暴露出的脏数据与脱敏问题

### 背景

在最初 1000 行 demo 中，TSV 转 JSONL 流程可以正常运行，且明显手机号、身份证号和 18 位以上长数字扫描没有残留。

但把处理范围扩大到前 10 万行后，发现 1000 行样本没有覆盖到更多真实脏数据类型。因此 10 万行验证必须作为后续数据工程的常规步骤，不能只依赖小样本判断质量。

### 现象

执行 10 万行导出：

```bash
cd /mnt/g/RAG/ragflow-learning-plan
PYTHONPATH=src python3 -m ragflow_style_pipeline.export_jsonl \
  --input /mnt/g/12345_pro_promax/data/t_order_master.tsv \
  --output outputs/t_order_master.100k.jsonl \
  --quality-report outputs/t_order_master.100k.quality.json \
  --limit 100000
```

初次扫描发现仍有编号类信息残留，主要包括：

- 前面带 `0` 的手机号形态。
- 手机号后面多一位的异常号码形态。
- 13～17 位纯数字编号，例如订单号、快递号、银行卡号、业务流水号。
- 字母加长数字的业务编号，例如快递单号、平台订单号、政务业务编码。
- 少量 TSV 结构污染：一条记录的正文里混入了后续字段、制表符或换行片段。

### 根因判断

1. 真实 12345 工单文本中，敏感信息不只包含“标准手机号”和“标准身份证号”。
2. 工单正文经常包含快递单号、平台订单号、银行卡号、业务流水号等长编号。
3. 原始 TSV 存在字段数量异常和嵌入换行问题；有些行字段数量看似可读，但正文实际已经混入其他字段。
4. 1000 行小样本不足以暴露这些问题，扩大样本后才出现更多边界情况。

### 处理方式

在 `src/ragflow_style_pipeline/pii_redactor.py` 中增强脱敏规则：

- 标准手机号和带前导 `0` 的手机号形态统一替换为 `[手机号]`。
- 18 位身份证号替换为 `[身份证号]`。
- 18 位以上纯数字替换为 `[长数字编号]`。
- 13～17 位纯数字替换为 `[数字编号]`。
- 字母加 10 位以上数字的业务编号替换为 `[业务编号]`。

在 `src/ragflow_style_pipeline/export_jsonl.py` 中增加结构污染跳过规则：

- 字段数量不匹配的行跳过。
- 生成后的文档正文中如果包含真实制表符或字面 `\t`，视为结构污染，跳过。

### 最终 10 万行验证结果

最终质量报告：

```json
{
  "rows_read": 100000,
  "documents_written": 99133,
  "rows_skipped_bad_field_count": 739,
  "rows_skipped_polluted_text": 128,
  "redactions": {
    "phone": 2839,
    "alnum_id": 108977,
    "id_card": 2350,
    "long_number": 615,
    "numeric_id": 294
  }
}
```

Python 精确扫描结果：

```text
phone_like: 0
id18_like: 0
numeric_13_17: 0
numeric_18_plus: 0
alnum_business_id: 0
literal_backslash_t: 0
actual_tab: 0
```

### 工程结论

- 做 RAG 数据前处理时，不能只看小样本“看起来正常”。
- 政务工单类 TSV 要先做结构质量检查，再做脱敏，再做 JSONL。
- 脱敏规则要覆盖“标准个人信息”和“业务编号类准敏感信息”。
- 异常结构行不要强行修复进 demo，第一版应直接跳过并计数，保证 RAG 样本干净。
- 生成的 `outputs/` 数据只能用于本地学习，不应提交到 GitHub。

## 8. 本地检索 Demo 暴露出的姓名脱敏问题

### 背景

在 10 万样本本地检索中，查询：

```text
拖欠工资 工地 工资 未发
```

Top-5 结果可以正确召回 `民生保障 / 劳动纠纷 / 拖欠薪资` 相关工单，但检索片段暴露了一个新问题：部分正文中存在 `姓名：某某` 形式的显式姓名。

### 根因判断

前一版脱敏规则主要覆盖：

- 手机号。
- 身份证号。
- 长数字编号。
- 字母加长数字的业务编号。

但没有覆盖 `姓名：xxx` 这种带明确标签的姓名模式。

### 处理方式

在 `src/ragflow_style_pipeline/pii_redactor.py` 中新增规则：

```text
姓名：2 到 8 个中文字符
  -> 姓名：[姓名]
```

同时在 `src/ragflow_style_pipeline/search_jsonl.py` 中做展示层二次脱敏：

- 终端只打印脱敏后的 `snippet`。
- `--output` 保存的 JSON 只包含安全 metadata 和脱敏后的 `snippet`。
- 不保存完整正文 `text`。

### 重新导出后的验证结果

1000 样本：

```json
{
  "rows_read": 1000,
  "documents_written": 995,
  "redactions": {
    "name": 9
  }
}
```

10 万样本：

```json
{
  "rows_read": 100000,
  "documents_written": 99133,
  "redactions": {
    "name": 1217
  }
}
```

安全扫描：

```json
{
  "documents_scanned": 99133,
  "possible_unredacted_phone": 0,
  "possible_unredacted_id_card": 0,
  "possible_unredacted_name_label": 0
}
```

### 工程结论

- 1000 样本只能验证流程，不足以证明脱敏规则完整。
- 10 万样本能暴露更多真实脏数据形态，应作为后续数据处理的常规验证规模。
- 规则脱敏只能覆盖“格式明确”的敏感信息。
- 没有明确标签的自由文本姓名，后续需要结合 NER、人工抽样审核和安全扫描闭环处理。
