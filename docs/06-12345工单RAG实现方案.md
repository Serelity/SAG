# 06 - 12345 工单 RAG 实现方案

本文把学习重点从“使用 RAGFlow”转为“参考 RAGFlow 的设计思想，为 `t_order_master.tsv` 实现一套 RAG 数据工程流程”。

## 一句话目标

把 12345 工单主表从原始 TSV 转换成可进入 RAG 系统的标准知识文档：

```text
原始 TSV
  -> 流式读取
  -> 字段筛选
  -> 数据清洗
  -> 隐私脱敏
  -> 工单文档化
  -> metadata 生成
  -> JSONL 输出
  -> 后续接入 RAGFlow / Elasticsearch / 向量库
```

## 为什么不直接把 TSV 丢进 RAG

这份数据有 98 万多行、129 个字段，属于结构化业务表。直接把整表当普通文本导入 RAG，会有几个问题：

- 字段太多，噪声远大于有效知识。
- 电话、身份证、姓名、录音 ID 等敏感信息不能直接进入知识库。
- 地区、分类、时间等字段更适合作为过滤条件，而不是全部混入正文。
- 大多数工单正文很短，不需要复杂切块；一行一个文档更合理。
- 有部分行字段数量不一致，需要单独记录并处理。

## 参考 RAGFlow 的核心思想

RAGFlow 的价值不只是“调用大模型”，而是把原始资料变成可检索知识单元。对应到你的 TSV 数据，应拆成几层：

| RAGFlow 思想 | 你的数据实现 |
| --- | --- |
| 文档解析 | 读取 TSV 每一行工单 |
| 文本规范化 | 把字段拼成稳定的中文文档文本 |
| 元数据建模 | 把地区、分类、时间、来源等字段作为 metadata |
| 隐私保护 | 对手机号、身份证、姓名等做脱敏 |
| Chunk 策略 | 第一版一行一个文档，超长工单后续单独切分 |
| 索引准备 | 输出 JSONL，供后续向量化和检索使用 |

## 第一版数据建模

### 一行 TSV = 一个 RAG 文档

原因：

- `case_content` 平均长度约 82 字。
- `case_goal` 平均长度约 16 字。
- 大多数工单是短文本诉求，不需要先切块。
- 工单天然有唯一 ID 和业务分类，适合“一行一文档”。

### 正文 text 字段

第一版正文建议由以下字段组成：

```text
诉求类型：{service_object_type}
诉求内容：{case_content}
诉求目标：{case_goal}
业务分类：{case_accord_type_one_name} / {case_accord_type_two_name} / {case_accord_type_three_name}
所属区域：{area_code_city} / {area_code_area} / {area_code_street}
来电时间：{call_time}
来源渠道：{order_source}
```

如果字段为空，就跳过该行文本，不强行输出 `NULL`。

### metadata 字段

第一版 metadata 建议保留：

```json
{
  "id": "...",
  "order_id": "...",
  "service_object_type": "...",
  "area_code_city": "...",
  "area_code_area": "...",
  "area_code_street": "...",
  "type1": "...",
  "type2": "...",
  "type3": "...",
  "order_source": "...",
  "order_type": "...",
  "order_status": "...",
  "call_time": "...",
  "call_month": "YYYY-MM"
}
```

metadata 的用途是精确过滤，例如：

```text
武进区 + 拖欠薪资 + 2025 年
```

不应该只依赖向量相似度。

## 字段分层

### 进入正文

| 字段 | 用途 |
| --- | --- |
| `case_content` | 用户原始诉求 |
| `case_goal` | 诉求目标/摘要 |
| `service_object_type` | 咨询、求助、投诉举报等 |
| `case_accord_type_one_name` | 一级业务分类 |
| `case_accord_type_two_name` | 二级业务分类 |
| `case_accord_type_three_name` | 三级业务分类 |
| `area_code_city` | 城市 |
| `area_code_area` | 区县 |
| `area_code_street` | 街道 |
| `order_source` | 来源渠道 |

### 作为 metadata

| 字段 | 用途 |
| --- | --- |
| `id` | 文档主键 |
| `order_id` | 工单编号 |
| `order_type` | 个人/企业等 |
| `order_status` | 工单状态 |
| `call_time` | 来电时间 |
| `case_complete_time` | 完成时间 |
| `belong_platform` | 所属平台 |
| `form_type` | 表单类型 |

### 脱敏后才可使用

| 字段 | 风险 |
| --- | --- |
| `call_number` | 电话号码 |
| `contact_number` | 电话号码 |
| `order_user_id` | 可能是身份证号 |
| `customerName` | 姓名 |
| `orderUserName` | 姓名 |
| `orderUserPhone2` | 电话号码 |
| `recordId` | 可能关联通话记录 |
| `order_sound_record_id` | 录音记录 ID |
| `attachment_ids` | 附件 ID |

第一版不把这些字段写入输出。正文中的手机号、身份证号也要替换成占位符。

### 第一版丢弃

大量流程字段、内部 ID、几乎全空字段先不进入 RAG，例如：

```text
process_instance_id
belong_dept
order_no
tenant_id
creator_id
updator_id
delete_flag
dispatch_flag
lockStatus
first_level_affiliation
second_level_affiliation
third_level_affiliation
fourth_level_affiliation
fifth_level_affiliation
sixth_level_affiliation
seventh_level_affiliation
```

## 输出格式

采用 JSONL，一行一个文档：

```json
{"doc_id":"ORDER_DOC_001","text":"诉求类型：求助\n诉求内容：……","metadata":{"area_code_area":"武进区","type3":"无照经营游商","call_month":"2024-06"}}
```

JSONL 的好处：

- 可以流式写入，适合大文件。
- 易于抽样检查。
- 易于后续导入 Elasticsearch、向量库或自定义 RAG 服务。
- 比 CSV 更适合保存嵌套 metadata。

## 第一版不做什么

第一版明确不做：

- 不调用 LLM。
- 不生成 embedding。
- 不改 RAGFlow 源码。
- 不把 98 万行一次性加载到内存。
- 不输出敏感字段。
- 不把原始 TSV 或脱敏前样本提交到 GitHub。

这样做是为了先把数据地基打稳。

## 成功标准

第一版完成后应能得到：

- 一份可复现的字段配置文件。
- 一个流式 TSV 转 JSONL 脚本。
- 一个脱敏模块。
- 一个文档构造模块。
- 一份小样本输出，例如前 1000 条脱敏工单。
- 一份质量报告：总行数、跳过行数、异常字段数、脱敏命中次数、输出文档数。

完成这些后，再考虑把 JSONL 接入 RAGFlow 或单独向量库。
